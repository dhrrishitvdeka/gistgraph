# M5: incremental updates, ablations, analysis

Goal: test H4 (streaming), run the controls that make H1-H3 interpretable, and turn raw result files
into tables whose claims come with uncertainty.

## Incremental memory (`model/streaming.py`) (H4)

A streaming memory receives the text in `chunks` consecutive pieces and may not look ahead. State
after each piece, per node: the raw write state `z`, the total write weight received (`mass`), and
the sum of weight times source position (for ordering).

For a new piece:

1. **Budget.** The node count after this piece is `floor(tokens_seen / ratio)`. It can only grow, so
   the memory always holds `N_seen / ratio` nodes and ends at the same size as in the one-shot
   case. (With the adaptive pool the budget is that of the pool, and the gates then act once at the
   end.)
2. **Encode** the piece alone, with its absolute position codes (`pos_offset`).
3. **Route** its segments over *all* current nodes (old and fresh), exactly as in M3.
4. **Merge.** A node that existed and receives weight `m_new` is updated as
   `z <- (1 - a) z_old + a z_new`. A fresh node takes `z_new`. A node that receives nothing keeps
   `z_old`.
5. After the last piece, the nodes go through the usual finalisation, gates, edges, message passing
   and projection, so the graph is built once from the final node states.

The merge coefficient is `a = sigmoid( logit(m_new / (m_old + m_new)) + correction )`. The prior term
is the *mass-weighted running average*, so each node stays the mean of everything written to it.
`correction` is a small learned network that outputs zero at initialisation. Therefore:

- a model **not** trained with streaming can still be run in streaming mode (zero-shot) and behaves
  as a running average;
- a model trained with `compressor.streaming.enabled: true` learns when to overwrite stale content
  or protect a node.

Total write mass is conserved (every segment writes weight 1 in total), which the tests check
for any chunking.

Streaming is compared with one-shot compression in two ways: the same trained weights evaluated with
`eval.stream_chunks: 4` (label `+stream4`), and a model trained with streaming (`graph_stream`).
The streaming encoder sees only the current piece, so a model trained one-shot (full bidirectional
context) pays a distribution-shift cost in zero-shot streaming. Separating that cost from the cost
of incremental merging is the reason for training a streaming-aware model as well.

## Ablation grid

| config | what changes against `graph` | tests |
|---|---|---|
| `graph_noedges` | edges off, same parameters | H1 |
| `graph_random` | random graph, equal degree | H1 |
| `graph_gumbel` | Gumbel top-k instead of entmax | design choice |
| `graph_stream` | trained with 4 chunks and a learned merge | H4 |
| `routed_fixed` / `routed_adaptive` (M3) | fixed rate versus gates | H2 |
| `flat` (M2) | no routing, no graph | H1, H3 |

All use the same data, steps, seed and budget. Every one is trained once per config (one seed), which
the results page states.

## Analysis (`eval/analysis.py`, `eval/results.py`)

- **Pairing.** Methods are compared example by example (`id`), never by comparing two means over
  different subsets.
- **Intervals.** A difference in F1 points carries a 95% percentile bootstrap interval (2000
  resamples of examples). A difference is marked `*` only if the interval excludes zero. These
  intervals capture which examples were drawn, **not** variation between training runs, because
  there is one training seed per model. The results page says so.
- **Retention** is a ratio of mean F1 values and is reported with the achieved compression ratio.
- **H1** compares `graph` with each control. **H2** compares `routed_adaptive` with `routed_fixed`
  and shows how much the per-document memory length varies (a fixed-rate model has none). **H3**
  splits the graph-versus-flat difference into single-hop, multi-hop and number of hops. **H4**
  compares each `+streamN` evaluation with its one-shot version.

`python -m gistgraph report runs/*` writes `docs/results/results.md` and the figures.

## Structure probe (`eval/probes.py`)

For HotpotQA the two supporting paragraphs are known. A node's *home paragraph* is the paragraph that
supplied most of the write weight it received. The probe measures the share of edge weight that
connects the homes of the two supporting paragraphs, divided by the share expected if the same
number of edges were placed uniformly at random between the active nodes. A value of 1 means no better
than random. It is computed on contexts that were not cut, so the paragraph bookkeeping is valid. It
is checked on synthetic graphs with known answers, and random graphs score about 1.

```bash
python -m gistgraph probe --config configs/experiments/m4_graph.yaml --ratio 4
```

## Reproduce everything

```bash
python scripts/run_experiments.py \
    configs/experiments/m2_flat.yaml \
    configs/experiments/m3_routed_fixed.yaml configs/experiments/m3_routed_adaptive.yaml \
    configs/experiments/m4_graph.yaml configs/experiments/m5_ablations/*.yaml \
    --stream-eval 4
python -m gistgraph baselines --config configs/experiments/m1_baselines.yaml
python -m gistgraph probe --config configs/experiments/m4_graph.yaml
python -m gistgraph report runs/m1_baselines runs/m2_flat runs/m3_routed_fixed \
    runs/m3_routed_adaptive runs/m4_graph runs/m5_graph_noedges runs/m5_graph_random \
    runs/m5_graph_gumbel runs/m5_graph_stream
```

Training resumes from its checkpoint if interrupted, and finished runs are skipped.

## Limits

One seed per model; a 0.5B frozen LLM whose full-context F1 is low; 200-example evaluation subsets;
a small training budget (1000 steps); contexts cut to 1536 tokens; query-aware baselines that the
learned compressors cannot match in access. Any positive or negative H1-H4 finding should be read
with these in mind, and a null result is a valid outcome.
